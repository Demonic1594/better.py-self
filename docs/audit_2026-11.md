# Codebase audit, November 2026 (audit round 3)

A full review of `discord/` (about 119,000 lines) against the two projects it
descends from:

- **dolfies/discord.py-self** `master` at `2ba64a9` (the commit recorded in
  `.github/LATEST_UPSTREAM_COMMIT.txt`; upstream has not moved since).
- **Rapptz/discord.py** `master` at `65232c3`.

The changelog for these changes is the `Unreleased` section of
`docs/whats_new.rst`. The regression tests are in
`tests/test_audit3_round1.py` and `tests/test_audit3_round2.py`. Where a fix touches code that still matched
upstream, `docs/upstream_syncing.rst` ("Audit round 3") lists it.

## Method

1. Baseline first: the test suite, ruff 0.12 and pyright 1.1.394 were all green
   on the unmodified code.
2. Twelve read-only review passes, one per area, each told to read its files in
   full, compare them with both upstreams, and report only defects with a
   concrete trigger: gateway and voice; HTTP and tracking; the two halves of
   `state.py`; client and utils; guild, member, role and user; messages and
   `abc`; channels and threads; `ext.commands` and `ext.tasks`; flags, enums,
   permissions and audio; settings, components, webhooks and audit logs; and
   the user-account-only models (applications, store, billing and so on).
3. Every reported finding was then checked against the code before anything
   was changed. Findings that did not hold, or whose fix would change
   behaviour users may rely on, were not applied (see "Rejected" and
   "Remaining issues").
4. One class of bug found along the way (a name imported only under
   `TYPE_CHECKING` but used at runtime) was then searched for mechanically
   across the whole package with an AST scan, which found one more instance.
5. Each fix got a regression test (66 in all). 65 of them fail on the previous
   code on any Python version. The remaining one covers the
   `asyncio.TimeoutError` catch in `voice_state.py`: that class is the builtin
   `TimeoutError` from Python 3.11 on, so the test can only fail on the 3.10
   leg of CI.

## Comparison with the upstreams

**dolfies/discord.py-self:** nothing to merge. `master` is still the synced
commit.

**Rapptz/discord.py:** every bug fix since June 2025 that applies to a user
account was checked and is already present here, in the same or an equivalent
form. Among them: the stuck rate limit bucket and hashed bucket key fixes, the
heartbeat latency race, reconnecting on the default gateway after a 5xx,
closing the socket on a poll timeout, zstandard without a size header, voice
v8, FFmpeg errors reaching `after`, `MessageType.is_deletable`, the
`Message.edit` suppress default, the file upload limit, the new pin endpoints,
the thread join `PUT`, `Thread.applied_tags` for media channels, the duplicate
`ForumChannel._flags` slot, `GUILD_MEMBER_ADD` for a cached member, the audit
log role-colour and category fallbacks, the Python 3.14 annotation fixes for
flags, and the `datetime.utcnow` / `asyncio.iscoroutinefunction` removals.
Permission bit values and the `Permissions` presets are identical in all three
projects.

Several of the bugs fixed below are also present in Rapptz/discord.py or
dolfies/discord.py-self today; those are marked **(upstream)**.

## What was fixed

### Could stop or stall the client

| Area | Problem | Fix |
| --- | --- | --- |
| Gateway | A `HELLO` without `heartbeat_interval`, or a `READY` without `session_id` / `resume_gateway_url`, raised `KeyError` out of the receive loop. That is not a reconnectable error, so `Client.connect` ended. | Logged as a warning; the socket is closed and the client reconnects (re-identifying when there is no session). |
| Gateway | A handshake that failed or was cancelled (the 60 second connect timeout) left its websocket open. | `from_client` closes the socket it opened. |
| Voice **(upstream)** | A lost IP discovery datagram during a voice reconnect was awaited with no timeout: voice died silently. | 10 second timeout. `connect()` then fails and disconnects, so it can be called again; a resume gives up and disconnects; the full reconnect after other close codes retries by itself. |
| Voice **(upstream)** | A failed or cancelled `channel.connect()` left the voice client registered, so every later `connect()` raised "Already connected". Only a timeout cleaned up. | Cleanup on any failure or cancellation. |
| Voice **(upstream)** | On Python 3.10, `except TimeoutError` did not catch `asyncio.TimeoutError`, so the timeout escaped `disconnect()` before its cleanup. | Catches `asyncio.TimeoutError`. |
| Member chunks | A chunk request whose reply never arrived stayed registered forever. Every later `Guild.chunk()` joined it and never returned. | Requests track their last activity; when another `chunk()` or `fetch_members()` call finds one silent for over a minute, it fails it and sends a new request. A single call whose reply is lost still waits (see "Remaining issues"). |
| Startup | An info API answer without `browser_user_agent` was accepted, and login then failed with `KeyError`. | Treated like any other unusable answer (fallback lookup). |

### Robustness, resources and logging

- **Leaks:** files the library opened from a path stayed open when `send()`
  rejected its arguments. A finished member list scrape could delete the
  registration of a newer scrape of the same guild. A cancelled ready task
  could clear the reference to its replacement.
- **Pre-connect state:** reading your own status or activities before the
  websocket exists (after a persistence replay) raised `AttributeError`.
- **Audio:** FFmpeg failures now reach `after` through `PCMVolumeTransformer`;
  the piped-input writer thread and `__del__` no longer raise on a
  cleaned-up or half-constructed source; the Opus encoder pads a short PCM
  buffer instead of letting libopus read past its end.
- **Malformed input:** unparsable rate limit headers on a webhook response and
  a relationship that references an unknown user in `READY_SUPPLEMENTAL` no
  longer raise.
- **Log redaction:** `billing_address` and `bank` are now masked in DEBUG logs
  of request bodies.
- **Deprecation:** `request_guilds` now emits the `DeprecationWarning` its
  documentation has promised since 2.1 (it was an open item on the roadmap).

### Performance

- `utils.SequenceProxy` (behind `Client.guilds`, `Guild.members`,
  `Guild.roles` and others) never cached its copy: the `cached_property` was
  stored under a name-mangled attribute that nothing read. Every index,
  iteration, `in` test and `len`-adjacent call copied the whole collection, and
  re-sorted it for sorted proxies. It now copies once. Indexing a 200,000 item
  proxy 200 times went from about 0.13 s to about 0.002 s. **(upstream)**
- The onboarding route put the guild ID into the route template, which created
  one rate limit and telemetry key per guild. It now uses a placeholder like
  every other route.

### CI hardening

The lint, build and test workflows now run with a read-only token
(`permissions: contents: read`) and a job timeout. The wiki workflow already
declared its own permissions.

## Rejected findings

These were reported by a review pass and found not to hold, or the suggested
change would have made things worse:

- **`Role.move(above=..., below=...)` "inverted".** It is not: `above` names
  the role that ends up above the moved role, as documented, and matches
  Rapptz.
- **`ContextProperties` "bypasses its constant table".** True, but using the
  table would drop the extra keys (guild, channel and so on) of a location
  context. The current behaviour is the correct one; a comment now says why.
- **Rejecting truncated Ogg pages.** Stopping playback kills FFmpeg mid-page,
  so raising there would report an error to `after` on an ordinary skip.
- **`audit_logs(oldest_first=True)` "ignores the limit while fetching".**
  Deliberate (see the changelog): Discord returns entries newest first, so
  the oldest N can only be found by walking the range.

## Remaining issues and recommendations

Not changed in this round, in rough order of value. Each needs either a live
account to confirm the payload shape, or a decision about behaviour.

1. **Voice handshake races** (inherited from Rapptz). A new
   `VOICE_SERVER_UPDATE` replaces the UDP socket without closing the old one,
   which can delay IP discovery by up to 30 seconds. `_wait_for_state` can
   miss a state change that happens between its check and its wait.
   `disconnect()` during a handshake unregisters the client but leaves the
   connector running. These need a voice server to test against.
2. **`UserSettings.edit(client_theme=MISSING)`** does not reset the theme as
   documented (the value is dropped). Low impact.
3. **Partial presence users.** `User._update_self` treats keys missing from a
   partial user (`public_flags`, `collectibles` and others) as cleared.
   Whether Discord omits them in practice needs a live capture.
4. **`Client.login` failing outside `async with`** leaves the HTTP session
   open until the client is closed or collected.
5. **`Client.close` and running event handlers.** Handlers still running at
   close are not cancelled or awaited (same as Rapptz); they may then use a
   closed session.
6. **`AudioPlayer.set_source`** does not clean up the source it replaces. A
   piped FFmpeg source swapped out this way stays alive. Calling `cleanup()`
   there would break callers that reuse the old source, so it was left.
7. **`tasks.Loop.stop()`** only takes effect after the current sleep, so one
   more iteration runs. This is the documented "graceful" behaviour, but it
   surprises people; `restart()` called twice logs a `RuntimeError`.
8. **Rate limit buckets.** The request that empties a bucket returns only
   after the bucket resets (`Ratelimit.__aexit__`), as in Rapptz. Returning
   first and deferring in the background would make the last request of a
   window faster.
9. **Typing subscriptions.** After `subscribe_to(typing=False)`, a reconnect
   subscribes to typing again (same as upstream; the intent is unclear).
10. **`raw_thread_member_remove`** is dispatched once per removed member with
    the same payload, and not at all for uncached threads (same as Rapptz).
    This fits the planned `on_raw_thread_update` work on the roadmap.
11. **Python 3.14 forward references.** `ext.commands` resolves command
    signatures with the default annotation format; a parameter annotated with
    a name defined later in the module may raise at decoration time on 3.14.
    `FlagConverter` already handles this. Not reproduced (CI on 3.14 passes).
12. **Regular expressions in `utils.escape_markdown` / `remove_markdown`** are
    quadratic on a few adversarial inputs. At Discord's 4,000 character limit
    this costs at most about 0.1 s; it only matters for much longer text.
13. **A lone `Guild.chunk()` with a lost reply** still waits forever:
    `ChunkRequest.wait` has no timeout, and the stalled-request check only
    runs when another chunk call comes in. Adding a timeout changes what
    `chunk()` returns or raises for very large guilds, so it needs a decision
    on the timeout and on what to do with members already received.
14. **Smaller model gaps:** `SyncWebhookMessage.channel` ignores `thread`;
    `GroupChannel._update` clears `recipients` if an update omits them;
    `Widget` defines `__eq__` without `__hash__`; `Entitlement.payment` is a
    slot that is never set; read states keyed by guild are not dropped when
    the guild is removed.

## Verification

Run on the final code (Python 3.13, with orjson):

- `ruff format --check` and `ruff check` with ruff 0.12: clean.
- `pyright discord` with pyright 1.1.394: 0 errors.
- `python -m pytest -q`: 773 passed, 1 skipped (707 before this round). The new tests and the log
  redaction tests also pass with the stdlib JSON parser.
- Sphinx build with `-n -W`: clean.
- Memory benchmark (`tests/memory_bench.py --members 50000`): 45.27 MiB
  retained before and after.
- Stress benchmark (`tools/stress_bench.py`): every gate passes except the
  soak RSS plateau (+10.8 MiB against an 8 MiB limit), which fails by the
  same amount on the previous code and is tracked on the roadmap as
  allocator behaviour, not a leak.
